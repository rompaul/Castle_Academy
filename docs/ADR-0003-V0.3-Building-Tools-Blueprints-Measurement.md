# ADR-0003: V0.3 Building Tools, Blueprints, and Measurement Plugins

**Status:** Proposed  
**Date:** 2026-11-05  
**Decision owner:** Product/Engineering owner  
**Related documents/issues:** CA-TECH-001 Plugin-First Architecture, CA-TECH-003 Data and Event Contracts, Product Master Plan (V0.3 = Building tools, blueprints, and measurement challenges)

## Context

V0.3 extends Castle Academy with three capability domains per the Product Master Plan roadmap (`00_Product_Master_Plan/README.md:55-56`):

1. **Building tools** — higher-order block operations beyond single-block place/remove (line, fill rectangle, copy/paste region).
2. **Blueprints** — save a selected block region as a reusable template and place it elsewhere in the world.
3. **Measurement challenges** — measure distance/area/volume between blocks and validate against a target, supporting the "Learn Through Building" philosophy (`00_Product_Master_Plan/README.md:15-16`).

A decision is needed on how these features are integrated without violating the plugin-first architecture and without bloating the renderer or shell.

## Decision drivers

- **Plugin boundaries:** Every executable feature is a standalone plugin (`CA-TECH-001:22-24`). Plugins depend only on Core public interfaces (`WorldState`, `EventBus`), never on other plugins' private modules (`CA-TECH-005:44-45`).
- **Data ownership:** World blocks are owned by World Core (`CA-TECH-003:75`, `CA-TECH-001:73-74`). Plugins mutate world state only through `WorldState.place`/`remove` (or `BuildingPlugin.place`/`remove`), never directly.
- **Event-driven:** Plugins notify via domain events (`world.block.placed`, `world.block.removed`, plus new `world.blueprint.saved/loaded`, `world.measurement.completed`).
- **No personal data:** Blueprints and measurements contain only block coordinates and IDs (`CA-TECH-005:9-11`).
- **Testability:** Each plugin has unit tests for deterministic domain logic (`CA-TECH-004:6`, `CA-TECH-001:109-111`).

## Options considered

1. **Three standalone plugins** (`BuildingToolsPlugin`, `BlueprintPlugin`, `MeasurementPlugin`), each registered and activated by the shell, communicating through `WorldState` and `EventBus`.
2. **Single combined plugin** with all three features in one module.
3. **Feature code embedded in `ThreeWorldRenderer` / `App`** (rejected — violates plugin separation).

## Decision

**Option 1:** Three standalone plugins under `src/plugins/`:

- `src/plugins/building-tools/BuildingToolsPlugin.ts` — line placement, rectangle fill, region copy/paste.
- `src/plugins/blueprint/BlueprintPlugin.ts` — save/load/list blueprints (JSON snapshot of block coordinates + blockId), place blueprint at an origin.
- `src/plugins/measurement/MeasurementPlugin.ts` — distance/area/volume measurement, challenge target + completion check.

Each plugin declares `id`, `name`, `version` ("0.3.0") and lifecycle `register/initialize/activate/deactivate/dispose` (`CA-TECH-001:42`). The shell (`GameCanvas`/`App`) instantiates, activates, and wires them into `gameRef` so UI can invoke save/load/measure actions.

New domain events (versioned per `CA-TECH-003:60`):
- `world.blueprint.saved` / `world.blueprint.loaded` / `world.blueprint.placed`
- `world.measurement.completed`

## Rationale

- Standalone plugins keep each feature small, testable, and independently disable-able (`CA-TECH-001:44`).
- Shared `WorldState`/`EventBus` avoids cross-plugin imports and duplicated sources of truth (`CA-TECH-003:82`).
- Versioned events permit safe payload evolution in V0.4+.

## Consequences

### Positive
- Each plugin is independently unit-testable (in-memory `WorldState`, no DOM/Three.js dependency).
- Blueprint and measurement data contain only coordinates and block IDs — no personal data.
- Shell remains thin; UI buttons map to plugin public methods.

### Negative / trade-offs
- More files/modules than a single combined module (acceptable for maintainability).
- Blueprint placement overlaps with `BuildingToolsPlugin` region paste; both operate through `BuildingPlugin.place` to keep world-state mutation centralized.

### Risks and mitigations
| Risk | Mitigation |
|---|---|
| Blueprint placed outside build area | `WorldState.place` already validates `isInsideBuildArea`; plugin returns false for out-of-area placements. |
| Large blueprint paste causes frame drop | V0.3 build area is fixed 32×32; re-evaluate if open-world generation arrives (V0.4+). |
| Measurement challenge target ambiguity | Challenge payload includes exact numbers; completion check is deterministic. |
